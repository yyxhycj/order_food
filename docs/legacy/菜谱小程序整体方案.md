# 菜谱小程序整体方案

日期：2026-05-14

## 1. 方案结论

本项目定位为“小范围朋友一起使用的私密菜谱分享小程序”，不再沿用商业点单系统的重后端架构。

最终技术方案定为：

```text
微信原生小程序
  + 微信云开发 CloudBase
  + 云数据库
  + 云存储
  + 少量云函数
  + 小程序内轻量管理能力
```

当前仓库已有微信原生小程序页面基础，可以保留前端项目骨架；但 `Express + MySQL` 后端、订单/商品/购物车/价格等商业点单概念，应逐步退出第一版主链路。

第一版目标不是做一个“大平台”，而是做一个朋友之间真的会打开、会发布、会点“想吃”、会互相回应的小工具。

## 2. 产品定位

产品名称暂定：朋友菜谱

一句话定位：

```text
朋友之间的私密菜谱分享和想吃请求小程序。
```

核心使用场景：

1. 我把自己会做的菜谱发上去。
2. 朋友看到后可以收藏、评论，或者点“想吃”。
3. 菜谱作者或管理员收到请求，可以标记接受、准备中、已完成、已拒绝。
4. 请求人可以看到自己的想吃记录和状态。

产品气质：

```text
轻、亲密、非商业、低压力、有生活感。
```

不做成外卖系统，不出现支付、配送、库存、订单金额等商业语义。

## 3. 第一版核心闭环

第一版只确保以下闭环完整可用：

```text
用户登录
  -> 浏览菜谱
  -> 查看菜谱详情
  -> 发布菜谱
  -> 点“想吃”
  -> 作者/管理员处理请求
  -> 用户查看请求状态
```

这条链路必须优先于所有扩展功能。

## 4. 为什么不用 MySQL 和 Express

当前项目使用 `Express + MySQL` 能工作，但对“小范围朋友使用”的目标过重。

主要问题：

1. 需要安装和维护 MySQL。
2. 需要维护数据库连接、环境变量、迁移脚本。
3. 需要部署和维护 Node 服务。
4. 本地开发、真机调试、上线链路更复杂。
5. 当前代码里已有大量点单系统遗留字段，继续沿用会扩大架构债。

微信云开发更适合本项目：

1. 小程序原生支持。
2. 登录凭证由云函数解析，业务数据统一使用 `users._id`。
3. 图片上传可以直接走云存储。
4. 数据库权限和云函数能覆盖当前需要。
5. 不需要自建服务器。
6. 对小范围使用成本更低。

因此，本项目不建议继续以 MySQL 作为第一版数据库。

## 5. 技术架构

### 5.1 前端

继续使用微信原生小程序。

保留理由：

1. 当前项目已经是微信小程序原生结构。
2. 目标只做微信小程序，不需要多端框架。
3. 原生小程序和云开发集成最直接。
4. 不引入 Taro、uni-app 等额外抽象，降低学习和维护成本。

### 5.2 数据层

使用微信云数据库。

主要集合：

```text
users
categories
recipes
requests
favorites
comments
```

其中 `comments` 可以第二阶段再实现，但第一版可以先保留数据设计。

### 5.3 文件存储

使用微信云存储。

用于：

1. 菜谱主图。
2. 菜谱步骤图。
3. 用户头像缓存或补充资料图。

### 5.4 服务端逻辑

使用云函数承载需要权限校验或写入保护的操作。

大部分公开读取可以由小程序直接读云数据库；涉及写入、状态变更、删除、权限判断的操作走云函数。

### 5.5 管理能力

不做独立 Web 后台。

第一版在小程序内做轻量管理入口：

1. 管理分类。
2. 管理所有菜谱。
3. 管理所有请求。
4. 配置管理员。

管理员身份通过 `users.role` 控制；首次初始化时可用环境变量辅助指定管理员。

## 6. 数据模型

### 6.1 users

用途：记录小程序用户和权限。

字段建议：

```js
{
  _id: string,
  openid: string,
  nickname: string,
  avatarUrl: string,
  bio: string,
  role: 'user' | 'admin',
  status: 'active' | 'disabled',
  recipeCount: number,
  requestCount: number,
  createdAt: Date,
  updatedAt: Date
}
```

说明：

1. `openid` 是微信登录凭证，只存在于 `users` 集合。
2. 菜谱、点菜、收藏、留言等业务数据统一通过 `users._id` 关联用户。
3. `role` 控制是否能进入管理入口。
4. 小范围使用时，管理员可以先手动配置。

### 6.2 categories

用途：菜谱分类。

字段建议：

```js
{
  _id: string,
  name: string,
  description: string,
  icon: string,
  sort: number,
  status: 'active' | 'inactive',
  createdAt: Date,
  updatedAt: Date
}
```

第一版分类可以很简单：

```text
家常菜
甜品
饮品
快手菜
聚餐
其他
```

### 6.3 recipes

用途：菜谱主体。

字段建议：

```js
{
  _id: string,
  title: string,
  description: string,
  coverImage: string,
  images: string[],
  categoryId: string,
  authorUserId: string,
  ingredients: [
    {
      name: string,
      amount: string
    }
  ],
  steps: [
    {
      text: string,
      image: string,
      sort: number
    }
  ],
  cookingTime: number,
  difficulty: 'easy' | 'medium' | 'hard',
  tags: string[],
  tips: string,
  status: 'draft' | 'published' | 'hidden' | 'deleted',
  viewCount: number,
  favoriteCount: number,
  wantCount: number,
  commentCount: number,
  createdAt: Date,
  updatedAt: Date
}
```

命名原则：

1. 使用 `recipe` 表达菜谱。
2. 不再使用 `product`、`dish`、`menu_item` 作为核心模型。
3. 不出现 `price`、`stock`、`sales` 等商业字段。

### 6.4 requests

用途：想吃请求。

字段建议：

```js
{
  _id: string,
  recipeId: string,
  recipeTitle: string,
  recipeCoverImage: string,
  requesterUserId: string,
  authorUserId: string,
  reason: string,
  status: 'pending' | 'accepted' | 'preparing' | 'done' | 'declined' | 'cancelled',
  statusText: string,
  note: string,
  createdAt: Date,
  updatedAt: Date,
  handledAt: Date
}
```

状态流转：

```text
pending
  -> accepted
  -> preparing
  -> done

pending
  -> declined

pending
  -> cancelled
```

说明：

1. `requesterUserId` 是发起请求的人，对应 `users._id`。
2. `authorUserId` 是菜谱作者，对应 `users._id`。
3. 作者和管理员可以处理请求。
4. 请求人可以取消 pending 状态的请求。

### 6.5 favorites

用途：收藏菜谱。

字段建议：

```js
{
  _id: string,
  recipeId: string,
  userId: string,
  createdAt: Date
}
```

约束：

```text
同一个 userId + recipeId 只能收藏一次。
```

### 6.6 comments

用途：菜谱评论。可以第二阶段实现。

字段建议：

```js
{
  _id: string,
  recipeId: string,
  userId: string,
  content: string,
  status: 'visible' | 'hidden' | 'deleted',
  createdAt: Date,
  updatedAt: Date
}
```

## 7. 页面结构

建议将页面逐步收敛为以下结构。

```text
pages/home/home
pages/recipe/detail/detail
pages/recipe/edit/edit
pages/requests/list/list
pages/requests/manage/manage
pages/user/profile/profile
pages/admin/admin
```

### 7.1 首页 pages/home/home

职责：

1. 展示已发布菜谱。
2. 支持搜索。
3. 支持分类筛选。
4. 支持最新、热门排序。
5. 进入菜谱详情。

替代当前：

```text
pages/menu/menu
```

### 7.2 菜谱详情 pages/recipe/detail/detail

职责：

1. 展示菜谱主图、标题、作者、描述。
2. 展示食材和步骤。
3. 收藏菜谱。
4. 发起“想吃”请求。
5. 如果是作者或管理员，允许编辑。

替代当前：

```text
pages/product/product
pages/recipes/detail/detail
```

### 7.3 发布/编辑菜谱 pages/recipe/edit/edit

职责：

1. 新建菜谱。
2. 编辑已有菜谱。
3. 上传主图和步骤图。
4. 保存草稿。
5. 发布菜谱。

整合当前：

```text
pages/recipes/create/create
```

### 7.4 我的请求 pages/requests/list/list

职责：

1. 查看我发起的想吃请求。
2. 查看请求状态。
3. 取消待处理请求。
4. 跳转回菜谱详情。

替代当前：

```text
pages/orders/orders
```

### 7.5 收到的请求 pages/requests/manage/manage

职责：

1. 作者查看别人对自己菜谱发起的请求。
2. 管理员查看全部请求。
3. 处理请求状态。

替代当前：

```text
pages/admin/orders/orders
```

### 7.6 我的页面 pages/user/profile/profile

职责：

1. 展示用户信息。
2. 进入我发布的菜谱。
3. 进入我收藏的菜谱。
4. 进入我发起的请求。
5. 进入我收到的请求。
6. 管理员显示管理入口。

### 7.7 管理页 pages/admin/admin

职责：

1. 管理分类。
2. 管理所有菜谱。
3. 管理所有请求。
4. 查看简单统计。

第一版管理页可以很轻，不做复杂图表。

## 8. 云函数设计

### 8.1 login

职责：

1. 获取当前微信登录凭证。
2. 如果用户不存在，创建 `users` 记录。
3. 返回用户资料、`users._id` 和权限。

返回示例：

```js
{
  user: {
    _id: string,
    nickname: string,
    role: 'user' | 'admin'
  },
  isAdmin: boolean
}
```

### 8.2 createRecipe

职责：

1. 校验登录。
2. 校验菜谱字段。
3. 写入 `recipes`。
4. 更新用户菜谱数。

### 8.3 updateRecipe

职责：

1. 校验登录。
2. 校验当前用户是作者或管理员。
3. 更新菜谱。

### 8.4 deleteRecipe

职责：

1. 校验登录。
2. 校验作者或管理员权限。
3. 软删除菜谱，将状态改为 `deleted`。

### 8.5 createRequest

职责：

1. 校验登录。
2. 校验菜谱存在且已发布。
3. 创建想吃请求。
4. 更新菜谱 `wantCount`。

### 8.6 updateRequestStatus

职责：

1. 校验登录。
2. 校验当前用户是菜谱作者或管理员。
3. 校验状态流转合法。
4. 更新请求状态。

### 8.7 toggleFavorite

职责：

1. 校验登录。
2. 如果未收藏则收藏。
3. 如果已收藏则取消收藏。
4. 更新菜谱 `favoriteCount`。

## 9. 权限规则

### 9.1 普通用户

可以：

1. 查看已发布菜谱。
2. 发布自己的菜谱。
3. 编辑自己的菜谱。
4. 收藏菜谱。
5. 发起想吃请求。
6. 查看自己的请求。
7. 处理别人对自己菜谱发起的请求。

不可以：

1. 修改别人的菜谱。
2. 删除别人的菜谱。
3. 处理与自己无关的请求。

### 9.2 菜谱作者

作者是普通用户的一种身份，不需要单独角色。

作者可以处理自己菜谱下的请求：

```text
pending -> accepted
accepted -> preparing
preparing -> done
pending -> declined
```

### 9.3 管理员

管理员可以：

1. 管理所有菜谱。
2. 管理所有请求。
3. 管理分类。
4. 禁用不合适内容。

管理员判断方式：

```text
users.role === 'admin'
```

## 10. 当前代码迁移策略

当前项目不建议一次性推倒重写。更稳妥的做法是“保留小程序骨架，替换数据和业务主线”。

### 10.1 保留

可以保留：

```text
app.json
app.js
app.wxss
project.config.json
images/
pages/user/profile/profile
部分 recipes 页面中的表单和展示思路
```

### 10.2 改造

需要改造：

```text
pages/menu/menu -> pages/home/home
pages/product/product -> pages/recipe/detail/detail
pages/recipes/create/create -> pages/recipe/edit/edit
pages/orders/orders -> pages/requests/list/list
pages/admin/orders/orders -> pages/requests/manage/manage
```

### 10.3 冻结

第一版先冻结：

```text
server/
pages/blind-box/
pages/game/
pages/reminders/
复杂 admin 统计
库存相关代码
价格相关代码
订单金额相关代码
```

冻结不等于删除。等核心闭环稳定后，再判断是否恢复。

### 10.4 删除或废弃概念

第一版不再使用：

```text
商品 product
购物车 cart
订单 order
价格 price
销量 sales
库存 inventory
支付 payment
配送 delivery
取餐 pickup
店铺 store
```

统一替换为：

```text
菜谱 recipe
想吃请求 request
收藏 favorite
平台 platform
朋友/作者 author
```

## 11. 第一版里程碑

### 阶段一：云开发接入和数据模型

目标：

1. 开通云开发环境。
2. 初始化云数据库集合。
3. 实现 `login` 云函数。
4. 小程序启动时获取用户身份。

验收标准：

1. 真机可以打开小程序。
2. 能拿到当前用户，并且业务关联使用 `users._id`。
3. 云数据库里自动创建用户记录。

### 阶段二：首页和菜谱详情

目标：

1. 首页展示云数据库中的菜谱。
2. 支持分类筛选。
3. 支持搜索。
4. 菜谱详情能展示食材和步骤。

验收标准：

1. 至少 5 条测试菜谱能正常展示。
2. 点击菜谱能进入详情页。
3. 图片能从云存储正常加载。

### 阶段三：发布菜谱

目标：

1. 用户可以创建菜谱。
2. 可以上传主图。
3. 可以添加多个食材。
4. 可以添加多个步骤。
5. 可以保存草稿或发布。

验收标准：

1. 用户发布的菜谱能出现在首页。
2. 作者能编辑自己的菜谱。
3. 非作者不能编辑。

### 阶段四：想吃请求

目标：

1. 用户能在菜谱详情发起“想吃”请求。
2. 用户能查看自己发起的请求。
3. 作者能查看自己收到的请求。
4. 作者能更新请求状态。

验收标准：

1. 请求能创建成功。
2. 请求状态能从待处理流转到已接受、准备中、已完成。
3. 请求人能看到状态变化。

### 阶段五：我的页面和轻量管理

目标：

1. 我的页面展示用户信息。
2. 展示我发布的菜谱。
3. 展示我收藏的菜谱。
4. 展示我的请求。
5. 管理员能进入管理页。

验收标准：

1. 普通用户看不到管理员入口。
2. 管理员可以管理分类和全部请求。

## 12. 后续扩展

核心闭环稳定后，再考虑以下功能：

1. 评论。
2. 点赞。
3. 菜谱标签。
4. 本周想吃榜。
5. 朋友聚餐菜单。
6. 菜谱盲盒。
7. 简单提醒。

扩展原则：

```text
每次只加一个能增强朋友互动的小功能，不做商业平台复杂度。
```

## 13. 第一版不做清单

明确不做：

1. 支付。
2. 外卖配送。
3. 库存管理。
4. 商家后台。
5. 多店铺。
6. 优惠券。
7. 复杂数据报表。
8. 营销活动。
9. 推荐算法。
10. 大规模用户体系。

这些功能会稀释产品目标，增加维护成本。

## 14. 代码命名规范

统一使用以下业务词：

```text
recipe      菜谱
request     想吃请求
favorite    收藏
comment     评论
category    分类
author      作者
admin       管理员
profile     个人资料
```

避免继续使用：

```text
product
cart
order
store
price
sales
stock
payment
```

如果短期因为迁移需要保留旧页面路径，应在代码注释中标注为 legacy，并尽快迁移到新路径。

## 15. 推荐下一步

下一步建议直接执行“云开发迁移一期”：

1. 在 `app.js` 接入 `wx.cloud.init`。
2. 增加云函数目录。
3. 实现 `login` 云函数。
4. 新建 `users/categories/recipes/requests/favorites` 集合。
5. 重做首页数据读取，把本地/Express API 数据源切到云数据库。

在这个阶段，不继续修 MySQL 相关问题，不继续扩展盲盒、游戏化、提醒。

## 16. 最终判断

当前项目已经有可用的小程序雏形，但架构方向需要从“点单系统”收敛成“朋友菜谱分享”。

最终建议：

```text
前端保留微信原生小程序。
后端放弃 Express + MySQL 主链路。
数据和文件迁移到微信云开发。
第一版只做菜谱、发布、收藏、想吃请求和状态流转。
```

这会让项目更轻，也更贴合“小范围朋友一起用”的真实需求。
