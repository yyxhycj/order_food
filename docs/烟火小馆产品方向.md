# 烟火小馆产品方向

日期：2026-05-15

## 1. 一句话

给家里用的小菜单。记录做过的菜，也能像点菜一样说“今天想吃什么”，再一起安排谁来做、什么时候做。

它不是外卖店、不是公开菜谱平台，也不是“老婆是主厨”的单向工具。谁都可以点菜，谁也都可以掌勺；“主厨”只是这一餐的安排，不是固定身份。

## 2. 产品语气

界面文案要像家里人说话，短、具体、不端着。

推荐用词：

- 菜谱在界面里叫 `菜单` 或 `这道菜`。
- 想吃请求在界面里叫 `点菜` 或 `想吃`。
- 收藏在界面里叫 `留着`。
- 作者在界面里尽量不说，换成 `家里人`、`我会做的`、`等我确认`。
- 管理员叫 `管小馆`。

避免用词：

- 不写“智能推荐”“高效规划”“专属主厨”这类 AI 味或营销味。
- 不强调平台、作者、用户增长、商业订单。
- 不把某个人固定成主厨。

## 3. 当前页面

底部四个入口：

- `菜单`：看家里的常做菜、搜索、按标签挑菜。
- `点菜`：看我想吃什么、哪些已经安排。
- `安排`：把今天或最近想吃的菜排一排，选择我来做、你来做、一起弄、先放着。
- `我的`：我的资料、我会做的、我留着的、等我确认的点菜。

详情页重点：

- 展示这道菜的图、食材、步骤、饭桌留言。
- 可以把菜 `留着`。
- 可以点 `想吃这个`，理由可以很随意。

## 4. 数据命名

为了不做无意义迁移，内部集合名和服务名暂时保持英文旧结构：

```text
recipes    菜单里的菜
requests   点菜记录
favorites  留着下次吃
comments   饭桌留言
users      家里人
categories 分类
```

代码里可以继续使用 `recipe/request/favorite` 这些内部名；但用户可见文案应统一到上面的产品语气。

## 5. 状态流转

点菜状态：

```text
等回应 -> 已安排 -> 在做了 -> 吃过了
等回应 -> 改天吃
等回应 -> 先不吃
```

谁可以处理：

- 点菜的人可以取消自己的点菜。
- 这道菜的创建人可以处理别人点这道菜。
- `管小馆` 可以处理全部点菜。

## 6. 加载策略

小程序页面不要为了等云函数空白很久。当前策略是：

- 首页、点菜、安排、我的统计优先读本地缓存，有旧数据先显示。
- 后台再刷新云函数结果。
- 云函数里避免不必要的用户查询和全量内存排序。
- `categoryId: "all"` 不应该让云函数走分类筛选。

如果以后要继续优化，优先补数据库索引和服务端分页，不要先做复杂前端 loading 动画。

## 7. 前端语法约束

当前项目没有打包 `@babel/runtime`，微信开发者工具会把部分新语法编译成运行时 helper。如果 helper 没进包，就会出现类似：

```text
module '@babel/runtime/helpers/arrayWithHoles.js' is not defined
```

因此，在 `app.js`、`pages/`、`components/`、`services/`、`utils/` 的小程序前端 JS 里先遵守：

- 不写数组解构：用 `const result = list[0]`。
- 不写对象展开或 rest：用 `Object.assign` 或逐个字段。
- 不写会依赖外部 Babel helper 的语法。

云函数运行在 Node 环境，可以稍微现代一点；但前端要优先稳定。
